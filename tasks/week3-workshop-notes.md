| 维度 | Cobo 赛道 | Z.AI 赛道 |

| 评审权重 | CAW 关键性 + 场景贴合 | 端到端闭环 + 复杂度 |

### 2. MVP 打磨方法

**MVP 三要素**：

1. **核心流程可跑通**
   - 不是 Demo 视频，是真正可运行的代码
   - 先跑通 happy path，再处理边界情况

2. **问题定义清晰**
   - 30 秒内讲清楚：你解决什么问题？给谁用？效果如何？
   - 避免「为了用 AI 而用 AI」

3. **可演示性**
   - 评委需要看到实际效果
   - 准备 2-3 个测试用例，确保稳定运行

**常见错误**：

| 错误 | 正确做法 |
|------|----------|
| 追求功能全面 | 先做核心 1-2 个功能 |
| 只做 PPT/概念 | 必须有可运行 Demo |
| 忽略 README | README 是第一印象 |
| 不写边界说明 | 说明安全边界和失败处理 |

### 3. 提交材料清单

**必须提交**：
- [ ] GitHub Repo + README
- [ ] Demo 链接或演示视频（3-5 分钟）

**加分项**：


### 4. Demo Day 表达技巧

**30 秒电梯演讲模板**：

> 「我们的项目 [名称] 解决了 [问题]。
> 通过 [技术方案]，实现了 [效果]。
> 目前已完成 [进度]，[下一步计划]。」

**Demo 演示结构**：

1. **开场**（30秒）：问题是什么？为什么重要？
2. **演示**（2分钟）：核心流程跑一遍
3. **技术**（1分钟）：关键技术和创新点
4. **总结**（30秒）：成果和下一步

**评委关注点**：
- ❌ 不关心你用了多 fancy 的技术
- ✅ 关心你解决了什么真实问题
- ✅ 关心你的方案是否可行
- ✅ 关心你的 Demo 是否稳定

## 关键收获总结

1. **MVP > 功能全面**：先跑通核心流程，再扩展
2. **README 是门面**：评委第一眼看 README
3. **Demo 必须稳定**：跑不通的 Demo 比没有更糟
4. **讲清楚问题**：技术再好，问题没讲清也白搭
5. **时间管理**：1 周时间，优先级比完美更重要
