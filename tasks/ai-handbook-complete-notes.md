# AI Foundation Handbook 完整笔记（11 章）

> 日期：2026-05-31 ~ 06-01

## 1. LLM（05.31）

核心：模型输出是候选结果，不是事实本身。

关键概念：
- Token：模型处理的基本单位，影响上下文容量/成本/信息完整性
- Embedding：向量映射，用于语义搜索/RAG，但不能替代事实校验
- Transformer：擅长在上下文中找模式，不等于拥有稳定数据库
- Hallucination：看起来合理但无法验证的内容，在带执行能力的系统里是流程风险
- Multimodal：处理更多真实工作界面，关键判断仍要回到结构化数据

在 AI×Web3 中的位置：LLM 处于理解和生成层，配合数据层/编排层/执行层/安全层。

---

## 2. Prompt（05.31）

核心：Prompt 是软约束，不是安全边界。

关键概念：
- Instruction：拆成四段 — 任务目标/可用输入/禁止行为/输出格式+失败格式
- Few-shot：少量示例让模型模仿，示例要跟 eval 一起维护
- Structured Output：JSON schema/函数参数，让后续代码能检查/拒绝/记录
- Prompt Injection：攻击者通过外部内容让模型忽略规则，Agent 场景尤其危险

防护：外部内容标记不可信 / 工具调用前参数校验 / 敏感动作 allowlist+human approval

---

## 3. Context（05.31）

核心：模型只能基于看见的上下文行动。

关键概念：
- Context Window：一次请求能处理的最大范围，大窗口≠完美使用
- Context Engineering：设计上下文进入模型的方式
- Memory：跨请求保留的信息，不能替代实时授权
- Knowledge Base：可检索的外部知识库，需要维护来源/时间/版本

上下文分五层：指令层/任务层/事实层/知识层/记忆层

---

## 4. RAG（06.01）

核心：RAG 的可靠性取决于证据链，不取决于向量库。

关键概念：
- Chunking：按结构切（标题/API/函数说明/标准小节），保留来源/版本/时间
- Vector DB：存向量+metadata（来源/版本/chain/更新时间/可信等级），先过滤再排序
- Retriever：不能只看语义相似度，要区分版本/环境/时间/来源
- Rerank：初步检索后重新排序，减少「标题相似但内容不对」的结果
- Citation：答案里的关键结论连接回来源，是用户验证答案的入口

核心原则：检索结果不是事实（只是候选证据）/ 引用要能回到原文 / 检索失败要允许拒答

在 AI×Web3 中：协议文档问答、合约接口解释、治理提案摘要、审计报告检索、SDK Copilot

---

## 5. Agent（06.01）

核心：Agent 是被约束的执行循环。目标/工具/状态/权限/停止条件缺一不可。

关键概念：
- Tool Use：让 Agent 从「会回答」变成「能做事」，但也让 Prompt Injection 变得危险
- Planning：模型生成的计划只是候选路线，不是授权
- State：可查询/可恢复/可审计的状态，不只放在 prompt 历史里
- Reflection：自我检查可以提高质量，确定性检查才能承载风险
- Multi-Agent：适合复杂工作流，但会放大协调问题

最危险的设计：让 Agent 同时拥有模糊目标/广泛工具/长期记忆/大额资产权限

在 AI×Web3 中：用户目标 → Agent 生成计划 → 只读自动/写入检查 → Simulation → 用户确认 → Wallet 执行 → 日志

---

## 6. Frameworks（06.01）

核心：框架是系统边界的表达，不是智能本身。先理解工作流，再决定用不用框架。

关键概念：
- LangChain：组件库，适合组合能力，不适合替你决定产品边界
- LangGraph：工作流和状态机，适合多轮工具调用/重试/人工确认/分支/恢复
- OpenAI Agents SDK：工具/handoff/guardrails/tracing 的可组合结构
- DSPy：把 prompt pipeline 写成可优化的程序，适合有明确数据集和评估指标的任务
- Learning Agent：学习能力要先进评估闭环，再进入生产系统

核心原则：简单链路先保持简单 / 长流程需要显式状态 / 框架要能退出

---

## 7. Vibe Coding（06.01）

核心：人负责方向/约束/验收，Agent 负责生成/修改/搜索/执行。

关键概念：
- Claude Code / Codex CLI：AI Agent 进入本地开发环境，关键价值是「能在 repo 里行动」
- Model/API Config：管理模型/API key/上下文窗口/工具权限/成本/日志
- GitHub/gh：版本控制是人类审查的关键线，让 Agent 多做局部 patch
- CLI/Script：读写文件前确认范围，修改外部状态的脚本先 dry run
- Repo Workflow：从 issue 提炼任务 → 搜索 → 最小 patch → 跑测试 → PR summary

核心原则：任务要小 / 上下文要准 / 验证要硬

---

## 8. MCP（06.01）

核心：模型不应直接拥有世界；应通过明确协议访问被授权的上下文和工具。

关键概念：
- Server：暴露 resources/tools/prompts，重点是边界（哪些只读/哪些有副作用）
- Client：发现 server 能力，负责用户确认/权限提示/会话隔离
- Tool Schema：不只是字段类型，还要说明用途/参数含义/必填/是否修改外部状态
- Permission：区分只读/写入、当前会话/长期授权、是否需要确认、是否可撤销

在 AI×Web3 中：MCP 负责工具发现和调用格式；Web3 账户系统负责最终权限和执行边界

---

## 9. Evaluation（06.01）

核心：不能被重复测量的 AI 行为，就不能被稳定改进。

关键概念：
- Harness：运行 eval 的框架（样本/评分规则/系统版本/配置/日志/报告）
- Golden Set：30-100 条高质量样本，覆盖正常/边界/容易误判/高风险/历史bug
- LLM-as-Judge：用模型给模型评分，不能被神化，需定期校准
- Regression：每修一个重要 bug 都变成 regression 样本
- Observability：线上观察系统行为（输入/检索/工具调用/输出/错误/反馈/成本）

在 AI×Web3 中：交易解释准确性/风险提示漏报/工具调用越界/拒绝不确定请求/Prompt Injection识别

---

## 10. Fine-tuning（06.01）

核心：Fine-tuning 改的是模型行为分布，不是产品系统边界。

关键概念：
- SFT：监督微调，适合固定格式/特定语气/领域术语，对数据质量非常敏感
- LoRA：参数高效微调，降低训练成本和显存需求
- PEFT：参数高效微调方法的统称
- Dataset：训练集/验证集/测试集/回归集，不要把测试集拿去训练
- Overfitting：模型把训练数据记得太死，对新样本表现变差

核心原则：先有 eval 再谈 fine-tuning / 先修数据再修模型 / 别用微调存实时知识

---

## 11. Inference（06.01）

核心：推理服务的核心不是「跑出答案」，而是在约束条件下交付可用答案。

关键概念：
- API Model：上手快/更新快/基础设施负担低，但要处理速率限制/超时/重试/账单/版本变更
- Local Model：隐私要求高/成本敏感/离线运行/深度定制，但受限于显存/上下文/并发
- Quantization：降低精度（FP16→INT8/INT4），可能降低输出质量
- Serving：模型部署成稳定服务（并发/队列/流式输出/缓存/监控/版本管理）

核心原则：质量有代价 / 部署改变边界 / 服务要可替换

在 AI×Web3 中：推理服务必须留下可审计记录（用了哪个模型/输入来源/输出/是否触发工具）

---

## AI Foundation 模块总结

11 章全部完成。核心收获：

1. **模型是推理层不是真相源** — LLM/Prompt/Context 三章
2. **外部知识要证据链** — RAG 的可靠性来自 chunk 来源+版本+citation
3. **Agent 的核心是约束** — 目标/工具/状态/权限/停止条件
4. **框架是工具不是银弹** — 先理解工作流再选框架
5. **评估驱动改进** — 没有 eval 的 AI 系统不可靠
6. **推理要可控可观测** — 延迟/成本/质量/隐私的平衡
